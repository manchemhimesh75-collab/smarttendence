2. Question 1 — 6 Marks

Q1.1 — Define Software Engineering. Explain the need for Software Engineering.
ANSWER

Definition 1: Software Engineering is an approach to develop software.

Definition 2: Software Engineering is a systematic, disciplined, quantifiable study and approach to the design, development, operation, and maintenance of a software system.

Need for Software Engineering:

  1. Dynamic Nature — Rapid change in user requirements; additional features added over time using SE practices.
  2. Cost Management — Cost management performed by different means.
  3. Quality Management — Better processes provide quality management.
  4. Scalability — Able to incorporate new changes.
Q1.2 — Explain the Dual Role of Software with examples.
ANSWER

Software takes on a dual role — it is a Product, and at the same time, the Vehicle for delivering a product.

As a Product:

  • Delivers computing potential embodied by computer hardware or broadly, by a network of computers.
  • Software is an information transformer — producing, managing, acquiring, modifying, displaying, or transmitting information that can be as simple as a single bit or as complex as a multimedia presentation.
  • Delivers the most important product of our time — information.

As a Vehicle:

  • Basis for control of the computer (Operating Systems).
  • Communication of information (Networks).
  • Creation and control of other programs (Software tools and environments).
  • Transforms personal data (e.g., financial transactions) so data can be more useful in a local context.
  • Manages business information to enhance competitiveness.
  • Provides a gateway to worldwide information networks (e.g., the Internet).
Q1.3 — List and explain the causes of Software Crisis.
ANSWER

Software Crisis is a term used in computer science for the difficulty of writing useful and efficient computer programs in the required time. The causes are:

  1. Maintenance cost of software is as expensive as development cost.
  2. Projects running over-time — not delivered on schedule.
  3. Less efficient software products.
  4. Low quality software.
  5. Software often did not meet requirements.
  6. Software was never delivered on time.

Q1.5 — Explain the 4P’s of Management Spectrum.
ANSWER

There are 4 critical components in software project planning known as the 4P’s:

  1. People — Includes from manager to developer, customer to end user. Highly skilled and motivated developers needed. Organizations that achieve high maturity in people management have higher likelihood of implementing effective SE practices.
  2. Product — The ultimate goal of the project. Product objectives, scopes, alternatives, and technical/management constraints should be established beforehand.
  3. Process — Provides the framework from which a comprehensive plan for software development can be established. Task sets (tasks, milestones, work products, QA points) enable framework activities to be adapted.
  4. Project — Where the project manager’s roles come into play. Must guide team members, delegate tasks, help when needed, and accomplish all requirements in the project scope.
Q1.6 — Describe the W5HH Principle of Project Management.
ANSWER

Boehm suggests an approach that addresses project objectives, milestones, schedules, responsibilities, management and technical approaches, and required resources. The W5HH principle leads to a definition of key project characteristics and the resultant project plan:

  1. Why is the system being developed? — Assess validity of business reasons for the software work.
  2. What will be done? — Identify key project tasks and milestones required by the customer.
  3. When will it be accomplished? — Help the team establish a project schedule.
  4. Who is responsible for a function? — Define role and responsibility of each team member.
  5. Where are they organizationally located? — Customer, users, and stakeholders also have responsibilities.
  6. How will the job be done technically and managerially? — Define management and technical strategy.
  7. How much of each resource is needed? — Develop estimation.

3. Question 2a — 8 Marks (Detailed)

Q2a.1 — Explain the Linear Sequential (Waterfall) Model with phases, advantages, disadvantages, and when to use.
ANSWER

Phases:

  1. Communication — Requirement gathering and analysis; Requirement Specification (SRS).
  2. Planning — Assessing progress against the project plan; perform required actions to maintain schedule.
  3. Modelling — Transform the requirements specified in the SRS document into a structure suitable for implementation.
  4. Construction — Coding and Testing; Unit testing, Integration testing, System testing.
  5. Deployment — Maintenance:
    • Corrective Maintenance: Correct errors not discovered in development.
    • Perfective Maintenance: Enhance functionalities based on customer request.
    • Adaptive Maintenance: Port the software to work in a new environment.

Advantages:

  • Simple and easy to understand.
  • Phases are processed one at a time.
  • Each stage is clearly defined.
  • Clear and well-understood milestones.
  • Reinforces good habits: define-before-design, design-before-code.
  • Works well for smaller projects where requirements are well understood.

Disadvantages:

  • Difficult for the customer to state all requirements explicitly.
  • Must complete a given stage before moving on to the next.
  • Some teams sit idle for other teams to finish.
  • Appropriate when requirements are well-understood and changes will be limited.

When to Use:

  • Requirements are very well known, clear, and fixed.
  • Product definition is stable; technology is understood.
  • No ambiguous requirements.
  • Ample resources with required expertise available.
  • The project is short.
Q2a.2 — Explain Scrum Framework: Roles, Events, Artifacts (3-5-3 Structure).
ANSWER

Scrum is an Agile software development method for managing complex projects where requirements change frequently. It follows an iterative and incremental approach.

Three Core Roles:

  1. Product Owner — Represents customers and stakeholders; manages product requirements; maximizes product value; manages the Product Backlog.
  2. Scrum Master — Servant-leader; ensures Scrum practices are followed; removes obstacles; supports the team.
  3. Scrum Team (Developers) — Self-organizing, cross-functional team (typically 3–9 members); responsible for creating a “Done” product increment.

Five Core Events:

  1. The Sprint — A fixed-length timebox (1 month or less) where the team creates a usable product increment.
  2. Sprint Planning — Defines what can be delivered and how; produces Sprint Goal and Sprint Backlog.
  3. Daily Scrum — 15-minute daily check-in to inspect progress toward Sprint Goal and adapt the Sprint Backlog.
  4. Sprint Review — Demo at end of Sprint to inspect the Increment and adapt the Product Backlog with stakeholders.
  5. Sprint Retrospective — Internal team meeting to inspect people, relationships, processes, and tools; plan improvements.

Three Core Artifacts:

  1. Product Backlog — An ordered, evolving list of everything needed in the product.
  2. Sprint Backlog — The set of items selected for the Sprint, plus a plan for delivery.
  3. Increment — The concrete sum of all Product Backlog items completed during a Sprint.
Q2a.3 — Explain COCOMO Model with three levels and project classifications.
ANSWER

COCOMO (Constructive Cost Model) was developed by Barry Boehm. It is a procedural cost estimation model for software projects.

Three Levels:

  1. Basic COCOMO — Provides a rough estimate based only on the size of the software (KLOC).
    Formula: Effort = a × (KLOC)b
  2. Intermediate COCOMO — Improves estimation by considering cost drivers (EAF — Effort Adjustment Factor).
    Formula: Effort = a × (KLOC)b × EAF
    Cost Drivers: Product attributes (reliability, complexity), Hardware attributes (memory, performance), Personnel attributes (experience, capability), Project attributes (tools, schedule).
  3. Complete COCOMO — Most advanced; divides the project into phases and applies cost drivers to each phase separately. For large systems with multiple sub-systems. Highly accurate.

Project Classifications:

TypeCharacteristicsExamples
OrganicWell-understood application; small team; prior experience with similar projectsData processing programs
SemidetachedMixed experience team; some experience on type of system to be developedCompilers, linkers
EmbeddedStrongly related to machine hardware; large teamOperating systems, real-time systems
Q2a.4 — Explain the Requirement Engineering Process with all 7 tasks.
ANSWER

Requirements Engineering (RE) refers to the process of defining, documenting, and maintaining requirements in the engineering design process.

7 Tasks:

  1. Inception — First phase; gives an outline of how to get started. Address: understanding of the problem, the people who want a solution, nature of the solution, communication and collaboration between customer and developer.
  2. Elicitation (Requirement Gathering) — Focuses on gathering requirements from stakeholders. Problems: Problem of Scope (unnecessary detail, ill-defined), Problem of Understanding (unclear between developer and customer), Problem of Volatility (requirements changing over time).
  3. Elaboration — Refines requirements gathered in first two phases. Main task: modeling activities and develop a prototype elaborating features and constraints using necessary tools and functions.
  4. Negotiation — Discussion on what is needed and what is to be eliminated. Discuss: availability of resources, delivery time, scope of requirements, project cost.
  5. Specification — Produces: written document, set of models, collection of use cases, prototype. Models include: ER diagrams, DFD, FDD, Data Dictionaries.
  6. Validation — Checking for errors and debugging. Verify: all requirements stated and met correctly, errors debugged and corrected, work product built according to standards. Uses formal technical review.
  7. Requirements Management — Identifying, controlling, tracking, and establishing requirements. Manages changes; new requirements emerge — prioritize and assess impact on overall system.
Q2a.5 — Explain Extreme Programming (XP) with Values and Practices.
ANSWER

XP is the most widely used agile process, originally proposed by Kent Beck. It is lightweight, efficient, low-risk, flexible, and predictable.

Five Values of XP:

1. Communication   2. Simplicity   3. Feedback   4. Courage   5. Respect

XP Practices:

  • Planning: User story cards, Release planning, Small releases, Iterative process, Stand-up meetings (F2F at same location).
  • Design: Simple design (keep things simple to meet current requirements), Spike solutions (for tough technical problems), Refactoring (reduce redundancy, eliminate unused functionality), CRC cards (Class-Responsibility-Collaborator).
  • Coding: Customer availability (as part of project), Paired programming (Driver/Supporter), Collective code ownership (all contribute, no bottleneck).
  • Testing: Unit testing, Continuous integration, No overtime, Conduct release plan meeting to change scope or reschedule delivery.

When to Use:

  • Constantly changing demands or requirements.
  • Customer not sure about functionality of the system.
  • Small projects with small teams (F2F meeting easier).
  • Projects involving new technology or research projects.
Q2a.6 — Explain the Risk Management Process with all 5 steps.
ANSWER

Risk Management is the process of identifying, analyzing, and controlling risks that may affect a software project’s cost, schedule, and quality.

5 Steps:

  1. Risk Identification — Detect and list all possible risks. Uses brainstorming (group discussion for new ideas) and risk list preparation (risks from previous projects).
  2. Risk Analysis — (a) Identify problems causing risk, (b) Probability of occurrence, (c) Impact of problem, (d) Assign values 1–10 to probability and impact, (e) Risk Exposure = Probability × Impact, (f) Order risks by exposure factor.
  3. Risk Estimation — Evaluate severity. Likelihood (P: 0 to 1 or percentage), Impact (I: cost, time, quality). Rank and prioritize risks from highest to lowest concern.
  4. Risk Mitigation & Planning — Strategies: Avoidance (eliminate risk completely), Reduction (reduce probability or impact), Transfer (shift risk to third party), Acceptance (accept and prepare contingency). Plan includes: description, strategy, responsible person, timeline, contingency plan.
  5. Risk Monitoring & Control — Continuously track identified risks; evaluate mitigation effectiveness; identify new risks; ensure risk responses are properly executed and adjusted.

Q2b.3 — List the 5 Types of Feasibility Study.
ANSWER
  1. Technical Feasibility — Analyzes current hardware, software, and technology. Assesses team skills, existing technology, maintenance and up-gradation ease.
  2. Operational Feasibility — Analyzes degree of service to requirements; how easy product will be to operate and maintain after deployment.
  3. Economic Feasibility — Cost and benefit analysis; detailed analysis of development cost; whether project is beneficial in terms of finance.
  4. Legal Feasibility — Analyzes legality: data protection acts, licenses, copyrights, certificates. Confirms legal and ethical requirements.
  5. Schedule Feasibility — Analyzes timelines and deadlines; how much time teams will take to complete the project. Great impact on organization.
Q2b.4 — Explain Risk Categories with examples.
ANSWER
  1. Project Risks — Threats to the project plan. If real, schedule slips and costs increase. Includes budget, schedule, personnel, resources, customers, requirements, project complexity and size.
  2. Technical Risks — Concerns about methods, implementation, interfacing, testing, maintenance. Ambiguity, changing requirements, technical uncertainty, insufficient team knowledge.
  3. Business Risks — Threaten feasibility of software. Sub-categories: Market Risk (product developed but nobody wants it), Strategic Risk (doesn’t fit business strategy), Sales Risk (no clear plan to sell).
  4. Management Risk — Senior management or responsible staff leaving the organization. Negatively affects decision-making and project continuity.
  5. Budget Risk — Losing control over project budget. Due to improper estimation, cost overruns, scope expansion, improper financial tracking.

5. Question 3a — 6 Marks (Descriptive)

Q3a.1 — Explain the Prototyping Model with types, advantages, disadvantages, and when to use.
ANSWER

Process:

Requirement Gathering → Quick Design → Build a Prototype → Initial User Evaluation → Refining Prototype → Implement Product & Maintain

Types of Prototype:

  1. Rapid Throwaway — Quick prototype; discarded after evaluation.
  2. Evolutionary Prototype — Evolves into the final product through iterations.
  3. Incremental Prototype — Built in increments; each increment adds functionality.

Advantages:

  • Customer gets partial product early → greater satisfaction.
  • New requirements easily accommodated.
  • Missing functionalities easily figured out.
  • Errors detected earlier → saves effort and cost.
  • Reusability for complex projects; design flexibility.

Disadvantages:

  • Costly.
  • Too much variation in requirements each time prototype is evaluated.
  • Difficult to accommodate all customer changes.
  • Uncertainty in determining number of iterations.
  • Developers may end up with sub-optimal solutions rushing to build prototypes.

When to Use:

  • Customer defines general objectives but does not identify detailed input, processing, or output requirements.
  • Developer unsure of algorithm efficiency, OS adaptability, or human/machine interaction form.
Q3a.2 — Explain the RAD Model with phases, features, advantages, and when not to use.
ANSWER

RAD (Rapid Application Development) is a “high-speed” adaptation of the linear sequential model using component-based construction. Fully functional system within 60–90 days.

Phases:

  1. Requirements Planning — Techniques like brainstorming to understand business problem; structured plan describing critical data, methods, processing.
  2. User Description — Take user feedback and build the prototype using developer tools.
  3. Construction — Refine prototype, deliver; all modifications and enhancements done.
  4. Cutover — Test interfaces between modules; use automated tools; acceptance testing by user.

Features:

  • Rapid Prototype — Quick initial views for customer.
  • Powerful development tools (CASE) — Reduced development time.
  • Active user involvement — Increases acceptability.

Advantages:

  • Reduced development time.
  • Increased reusability of components.
  • Quick initial reviews; customer feedback encouraged.
  • Integration from beginning solves integration issues.

When NOT to Use:

  • Users cannot be involved continuously.
  • Tools and reusable components cannot be used.
  • Highly skilled developers not available.
  • Software cannot be modularized.
Q3a.3 — Explain Adaptive Software Development (ASD) with its three phases.
ANSWER

ASD evolved from RAD practices. Jim Highsmith published it in 2000. It is an iterative technique for building complex software systems, focusing on collaboration and team self-organization.

Three Phases:

  1. Speculation — Adaptive cycle planning using three types of information:
    • Customer’s mission statement
    • Project constraints (delivery date, budgets, user description)
    • Basic requirements of the project

    This defines the set of release cycles.

  2. Collaboration — Collaboration among team members is key. Required qualities: assist each other without offense, work hard, possess required skill set, communicate problems, criticize without hate.
  3. Learning — Three ways team members learn:
    • Focus Groups — Direct feedback from end-user about component being developed.
    • Formal Technical Review — Performed by committee of 3–5 people ensuring quality.
    • Postmortems — Self-assessment by team; make appropriate improvements.
Q3a.4 — Explain Scheduling Techniques: Gantt Chart, PERT, CPM.
ANSWER

Scheduling is the process of planning and organizing tasks over time to ensure project completion within the specified deadline. It involves assigning start/end dates and allocating resources.

Techniques:

  1. Gantt Chart — Shows tasks vs time. Visual representation of task durations, start/end dates, and progress. Helps in keeping track of timeline for all project tasks.
  2. PERT (Program Evaluation Review Technique) — Handles uncertainty in task duration. Uses probabilistic time estimates (optimistic, pessimistic, most likely).
  3. CPM (Critical Path Method) — Identifies the critical path, which is the sequence of tasks that determines the minimum completion time. Any delay in critical path activities directly impacts the overall project schedule. Identifies inter-task dependencies for concurrent activities.
Q3a.5 — Explain RMMM Plan with Risk Mitigation, Monitoring, and Risk Plan.
ANSWER

An RMMM Plan is a document that defines how each identified risk will be handled, tracked, and controlled throughout the project. It considers three important issues:

1. Risk Mitigation (Avoidance):

Focuses on reducing or eliminating risks before they occur. Best strategy for proactive approach.

Example — High Staff Turnover:

  • Meet with current staff to identify causes of turnover.
  • Mitigate identified causes under project management control.
  • Assume turnover will occur; develop techniques for continuity.
  • Organize teams so knowledge is widely shared.
  • Define documentation standards; peer reviews for all work.
  • Assign backup staff for every critical technical role.

2. Risk Monitoring (Tracking):

Continuously tracking risks during the project. Monitor factors indicating whether risk is becoming more or less likely. For high staff turnover: monitor team attitudes, interpersonal relationships, outside job availability, and effectiveness of mitigation steps.

3. Risk Plan:

Document including how risks are identified and analyzed, steps to reduce risks, methods to monitor risks. Alternative: RIS (Risk Information Sheets) stored in databases for easier handling.

Q3a.6 — Explain Software Measurement: Need, Characteristics, Types.
ANSWER

Software metrics are the standards for estimating the quality, progress, and health of software development activity. A software metric is a quantifiable or countable assessment of the qualities of software.

Need:

For analyzing software performance, planning work items, estimating productivity, monitoring distinct statistics and trends as production takes place.

Characteristics of Software Metrics:

  • Quantitative — Can be stated numerically.
  • Understandable — Simple to grasp; method well explained.
  • Applicability — Applied during early stages of development.
  • Repeatable — Same values when measured regularly and consistently.
  • Economical — Computation should be cost-effective.
  • Language agnostic — Not dependent on any programming language.

Types:

  • Internal Metrics — Measure properties important to developers (e.g., Lines of Code).
  • External Metrics — Measure features important to users (portability, reliability, functionality, usability).
  • Hybrid Metrics — Mix product, process, and resource metrics (e.g., Cost per FP).

Q3b.2 — List the Software Myths (3 categories with key myths).
ANSWER

Management Myths:

  • Myth 1: We already have a book of standards and procedures — Reality: Is it used? Is it modern? Complete? Streamlined?
  • Myth 2: We have the newest computers and tools — Reality: CASE tools more important than hardware; majority still don’t use tools effectively.
  • Myth 3: We can add more programmers and catch up — Reality: Not mechanistic; newcomers need education; add only in planned manner.
  • Myth 4: Outsource and relax — Reality: If can’t manage internally, will struggle when outsourcing.

Customer Myths:

  • Myth 1: General statement of objectives is sufficient — Reality: Formal detailed description essential; effective communication needed.
  • Myth 2: Requirements change but change can be easily accommodated — Reality: Impact varies with timing; early changes easy.

Practitioner (Developer) Myths:

  • Myth 1: Job done when program works — Reality: 60% to 80% of effort expended after first delivery.
  • Myth 2: Cannot achieve quality until program runs — Reality: Formal technical reviews from beginning; more effective than testing for certain defects.
  • Myth 3: Only deliverable is working program — Reality: Documentation, models, plans provide foundation for support.
  • Myth 4: SE is about creating unnecessary documentation — Reality: SE is about creating quality; better quality → reduced rework → faster delivery.

Q3b.7 — List Software Quality Metrics (8 metrics).
ANSWER
  1. Code Quality — Quantitative (LOC, complexity, bug generation rate) and Qualitative (readability, clarity, efficiency, maintainability).
  2. Reliability — Checked using Mean Time Between Failure (MTBF) and Mean Time To Repair (MTTR).
  3. Performance — Whether software fulfills user requirements; analyzing time and resource utilization.
  4. Usability — Whether the program is user-friendly; end-user satisfaction.
  5. Correctness — Degree to which software performs its required function.
  6. Maintainability — Ease with which program can be corrected, adapted, or enhanced. Measured by Mean Time To Change (MTTC).
  7. Integrity — System’s ability to withstand attacks (accidental and intentional) to its security.
  8. Security — No unauthorized changes, no fear of cyber attacks when software is in use.

9. Memory Aids & Answer Writing Tips

Memory Aids

Agile Manifesto: “Individuals Working Customer Responding” (IWCR)
Scrum 3-5-3: 3 Roles, 5 Events, 3 Artifacts
RE 7 Tasks: I-E-E-N-S-V-M (Inception, Elicitation, Elaboration, Negotiation, Specification, Validation, Management)
COCOMO Levels: Basic → Intermediate → Complete
Risk Process: ID → Analysis → Estimation → Mitigation → Monitoring
Feasibility: TOELS (Technical, Operational, Economic, Legal, Schedule)
XP Values: CSFRC (Communication, Simplicity, Feedback, Respect, Courage)

Answer Writing Tips

  1. Use exact PDF terminology — “Dual role”, “4P’s”, “W5HH”, “3-5-3 structure”
  2. Structure answers: Definition → Points → Example/Explanation
  3. For 8-mark questions: Detailed phases/steps with sub-headings
  4. For 4-mark questions: Bullet points, tables for comparisons
  5. For 6-mark questions: Balanced detail (not too brief, not too long)
  6. Include examples from PDF (Library Management System, Banking software, etc.)
  7. Draw diagrams where applicable (Waterfall phases, Scrum 3-5-3, CPM network)
